## 解读

### 1. 单请求收益大，高并发收益缩小

- chat 并发 1：AWQ 总输出吞吐 +39.6%；TPOT 18.7→12.8ms，下降 31.6%，decode 速度尺度约 53.5→78.1 tok/s（+46.1%）。总吞吐与 decode 速度不同，不要混用百分比。
- chat 并发 16：吞吐 +12.6%；并发 32：+6.6%；并发 64：+10.2%。
- 这符合低并发可能更受权重读取带宽影响、高并发计算和调度等开销占比上升的解释。日志已确认两个版本使用 Marlin weight-only 路径、TP all-reduce 使用 PYNCCL；没有 profiling，仍不能据此独断主瓶颈。
- AWQ chat 并发 32→64：吞吐只 +5.0%，TPOT 83.4→169ms，约翻倍；高并发仍存在吞吐与响应体验的取舍。

### 2. 更大缓存不保证所有延迟指标更好

- chat 并发 64 的 AWQ TTFT 10.832→3.204s（约 -70.4%），但 TPOT 140→169ms（约 +20.7%）。总吞吐更高与每个请求 decode 更慢可以同时发生。
- 运行日志采样支持实际驻留差异：chat 并发 64，FP8 最大 Running=50、缓存使用率达 99.2%；AWQ 最大 Running=64、缓存最高 68.7%。这是更大缓存改变驻留并发的证据，但不等于证明某种 batch 分布或发生抢占；两份日志均未发现抢占/重计算消息。
- chat 并发 2 的 AWQ TTFT 也更高（962.6 vs 779.9ms）。只有一轮，不能把小幅变化视为稳定差异，亦不能宣称所有指标都优于 FP8。

### 3. Long 高并发没有随着缓存近翻倍而大幅改善

- long 并发 1 吞吐 +25.3%，并发 4 +14.5%，并发 16 仅 +6.8%。
- long 并发 16 TPOT 244.8→228.8ms（-6.5%），生成速度尺度仍约 4.4 tok/s。
- 日志采样中 long 并发 16 的 AWQ 缓存最高约 46.9%，FP8 为 86.2%，两者均观察到 Running=16。AWQ 缓存并未接近耗尽却仍慢，说明不能只靠增加缓存解决此 workload 的延迟。长输入 prefill/decode 干扰、计算与通信开销值得继续检查。

## 原始结果与日志补充结论

- **本轮 FP8 不是原生 W8A8 计算**：实际 kernel=`MarlinFP8ScaledMMLinearKernel`，日志明确说明使用 weight-only FP8 compression。AWQ=`MarlinLinearKernel`。更正“4090 一定走原生 FP8”的前期说法；不能把本轮结果外推成原生 FP8 Tensor Core 性能比较。
- 两版本的自定义 all-reduce 都因 GPU P2P 不可用或测试失败被禁用，实际使用 NCCL 2.29.7 / PYNCCL；不把“没有 NVLink”等同于“没有 P2P”，也不把警告当作通信瓶颈的量化证明。
- 首 token 尾延迟远高于中位数：chat 并发 16 的 TTFT p99 为 FP8 7.99s、AWQ 7.81s；并发 64 为 45.50s、33.19s。long 并发 16 为 60.88s、55.81s。
- AWQ chat 并发 16/64 的 ITL p99 为 760.3/951.4ms，表明流式输出中存在接近一秒的停顿。TPOT 与 ITL 不是同一个指标。
- 若示例 SLO 为 chat TTFT p99<2s，本轮仅并发 1/2/4 档符合，不能仅依据 p50 推荐并发 8～16；低档仅 16 个请求，仍需更多样本和开放式流量验证。
- 自动报告的“单请求生成速度”是 `1000/TPOT mean`，与前文 `1000/TPOT p50` 的速度尺度略有不同，不应混用。

## 当前选择与限制

若只看本机本轮显存与性能，AWQ 是更有利的候选：权重占用更低，测试中每个档位的总吞吐都更高。但不能据此做最终生产选型：

- 尚未做独立效果评测，不能证明 4bit 精度足够或比 FP8 更好。
- 已核查原始 JSON 的长度、p99 和 ITL，但小样本闭环测试仍不能给生产 SLO 并发保证。
- 仅各跑一轮，未检验波动和运行顺序影响。
- 实际 kernel 与通信后端已确认；未做 profiling 或读取抢占计数，不能确定主瓶颈，也不能保证没有抢占。
- 2×24GB 无法提供 27B BF16 对照；需要另租更大显存硬件。
